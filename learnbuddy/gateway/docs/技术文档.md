## 1. 概述

### 1.1 背景

实现一套 **Web 端 ↔ Gateway ↔ Desktop 端** 的双向实时消息推送系统，支持高并发、可靠投递、水平扩展。

### 1.2 架构概览

```
┌─────────────┐     WebSocket      ┌──────────────────┐    WebSocket/TCP   ┌─────────────┐
│   Web 客户端  │ ◄──────────────► │     Gateway      │ ◄───────────────► │  Desktop 端  │
│ (Browser)    │                   │  (Push Gateway)  │                   │ (Native App) │
└─────────────┘                   └──────────────────┘                   └─────────────┘
```

### 1.3 核心目标

| 目标 | 说明 |
|------|------|
| 实时性 | 消息延迟 < 500ms（P99） |
| 可靠性 | 至少一次送达（at-least-once） |
| 扩展性 | 支持水平扩展至 100K+ 并发连接 |
| 统一协议 | Web 与 Desktop 使用统一消息帧格式 |

## 3. 消息协议

### 3.1 消息帧格式

统一 JSON 格式：

```typescript
interface MessageFrame {
  type: 'push' | 'ack' | 'ping' | 'pong' | 'auth';
  id: string;                              // UUID v4
  from: string;                            // 发送方标识
  to: string;                              // 接收方 userId | sessionId | 'broadcast'
  payload?: Record<string, unknown>;       // 业务数据
  timestamp: number;                       // Unix ms
  ttl?: number;                            // 生存时间（秒）
}

interface AckFrame extends MessageFrame {
  type: 'ack';
  ackMsgId: string;                        // 被确认的消息 ID
  status: 'ok' | 'failed';
}
```

### 3.2 消息类型

| 类型 | 方向 | 用途 |
|------|------|------|
| `auth` | Client → Gateway | 连接鉴权 |
| `ping` | 双向 | 心跳检测 |
| `pong` | 双向 | 心跳回复 |
| `push` | 双向 | 业务消息推送 |
| `ack` | 双向 | 消息确认 |

## 4. 核心模块设计

### 4.1 Connection Manager（连接管理器）

```typescript
interface Connection {
  id: string;
  userId: string;
  type: 'web' | 'desktop';
  status: 'active' | 'idle' | 'reconnecting';
  lastHeartbeat: number;
  metadata: Record<string, string>;
  send(frame: MessageFrame): Promise<void>;
  close(): Promise<void>;
}

class ConnectionManager {
  // 连接路由表
  private sessions: Map<string, Connection>;
  private userSessions: Map<string, Set<string>>;

  /** 注册新连接 */
  register(conn: Connection): void;

  /** 注销连接 */
  unregister(sessionId: string): void;

  /** 获取用户的所有连接 */
  getByUser(userId: string): Connection[];

  /** 获取指定 session */
  getBySession(sessionId: string): Connection | undefined;

  /** 向用户所有连接发送消息 */
  sendToUser(userId: string, frame: MessageFrame): Promise<SendResult[]>;

  /** 获取在线用户数统计 */
  getStats(): ConnectionStats;
}
```

**数据结构设计（Redis 共享）**：

```
Key: gateway:sessions:{sessionId}
Value: {
  "userId": "user_xxx",
  "type": "web",
  "status": "active",
  "lastHeartbeat": 1716379457000,
  "gatewayId": "gw-1",
  "metadata": {}
}
TTL: 300s（心跳续期）

Key: gateway:users:{userId}
Value: Set<sessionId>  // 用户的所有活跃 session
```

### 4.2 Router（消息路由器）

```
消息到达 Gateway
      │
      ▼
   解析 to 字段
      │
      ├── "broadcast" ──────► 遍历所有连接投递
      │
      ├── 指定 sessionId ──► 查 ConnectionManager → 投递到目标连接
      │
      └── 指定 userId ────► 查 userSessions → 找到该用户所有连接
                              │
                              ├── Web 连接 → 并行投递
                              └── Desktop 连接 → 并行投递
```

### 4.3 心跳与保活

| 端 | 间隔 | 超时阈值 | 动作 |
|---|------|---------|------|
| Web → Gateway | 30s | 90s（3次） | 超时 → close → 客户端重连 |
| Desktop → Gateway | 60s | 180s（3次） | 超时 → 标记离线 → 等待重连 |

### 4.4 可靠投递（Reliable Delivery）

```
投递流程:
1. Gateway 收到 push 消息 → 分配 msgId (UUID v4)
2. 写入 PendingQueue: { msgId, targetId, frame, retries: 0, timestamp }
3. 投递给目标连接
4. 启动 ACK 定时器（默认超时 10s）
5. 收到 ACK → 从 PendingQueue 移除 → 完成
6. 超时 → retries++ → 重试（最多 3 次, 间隔 5s/10s/20s）
7. 3 次重试均失败 → 存入离线消息队列
```

```typescript
class ReliableDelivery {
  private pendingAcks: Map<string, PendingMessage>;

  async send(targetId: string, frame: MessageFrame): Promise<DeliverResult>;

  handleAck(ackMsgId: string): void;

  private async retry(msgId: string): Promise<void>;
}
```

### 4.5 离线消息存储

```typescript
interface OfflineStorage {
  /** 缓存离线消息 */
  cache(userId: string, message: StoredMessage): Promise<void>;

  /** 拉取用户离线消息（拉取后清除） */
  flush(userId: string): Promise<StoredMessage[]>;

  /** 获取离线消息数量 */
  count(userId: string): Promise<number>;
}
```

Redis 实现：

```
Key: gateway:offline:{userId}
Type: List
操作: RPUSH 存入, LPOP/LRANGE 取出
TTL: 7 天（过期自动清理）
```

## 6. 技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 运行时 | Node.js 20+ | 高并发 I/O，原生 WebSocket |
| 框架 | Fastify + @fastify/websocket | 高性能 HTTP + WS 一体 |
| 语言 | TypeScript 5.x | 类型安全，维护性好 |
| 共享状态 | Redis 7+ | 分布式连接表、消息队列 |
| 消息队列 | Redis Stream / BullMQ | 离线消息缓冲 |
| 日志 | Pino | 结构化日志，低性能开销 |
| 测试 | Vitest + Playwright | 单元/集成/E2E |
| Desktop 协议 | WSS (WebSocket Secure) | 统一协议栈，防火墙兼容 |
| 鉴权 | JWT (jsonwebtoken) | 轻量无状态 |

## 7. 部署架构

```
                          ┌─────────────┐
                          │  Nginx LB   │
                          │  (SSL 终结)  │
                          └──────┬──────┘
                                 │
              ┌──────────────────┼──────────────────┐
              ▼                  ▼                  ▼
        ┌──────────┐      ┌──────────┐      ┌──────────┐
        │ Gateway 1│      │ Gateway 2│      │ Gateway N│
        │ (gw-1)   │      │ (gw-2)   │      │ (gw-n)   │
        └─────┬────┘      └─────┬────┘      └─────┬────┘
              │                  │                  │
        ┌─────▼──────────────────▼──────────────────▼─────┐
        │               Redis Cluster                      │
        │   • 连接路由表  • pending_acks  • 离线消息       │
        │   • Pub/Sub 跨 Gateway 转发                      │
        └──────────────────────────────────────────────────┘
```

### 水平扩展要点

1. **Nginx Sticky Session** — WebSocket 连接保持同一直连
2. **Redis Pub/Sub** — Gateway 收到跨节点消息时通过 Pub/Sub 转发
3. **无状态设计** — Gateway 重启后从 Redis 恢复路由信息
4. **自动扩缩容** — 基于连接数指标

## 8. 错误码定义

| 错误码 | 含义 | 处理方式 |
|--------|------|---------|
| `AUTH_EXPIRED` | Token 过期 | 客户端重新获取 token 重连 |
| `AUTH_INVALID` | Token 无效 | 拒绝连接 |
| `SESSION_NOT_FOUND` | 目标 session 不存在 | 返回错误给发送方 |
| `USER_OFFLINE` | 用户离线 | 自动走离线消息流程 |
| `DELIVERY_TIMEOUT` | 投递超时 | 自动重试 |
| `RATE_LIMITED` | 频率限制 | 客户端指数退避重试 |

## 9. 消息流转完整示例

```
场景：Web 用户 A 向 Desktop 用户 B 推送消息

1. Web A 连接 Gateway (ws://gateway.example.com)
   → 发送 auth (JWT token)
   ← 收到 sessionId: "sess_web_A"

2. Desktop B 连接 Gateway (wss://gateway.example.com)
   → 发送 auth (JWT token)
   ← 收到 sessionId: "sess_desk_B"

3. Web A 发送 push 消息:
   {
     "type": "push",
     "id": "msg_001",
     "from": "user_A",
     "to": "user_B",
     "payload": { "text": "Hello Desktop B!" },
     "timestamp": 1716379457000
   }

4. Gateway 收到消息:
   a. Router 解析 to="user_B"
   b. 查 Redis: gateway:users:user_B → ["sess_desk_B"]
   c. 查 Redis: gateway:sessions:sess_desk_B → { gatewayId: "gw-1" }
   d. 本机 → 直接投递; 跨节点 → Redis Pub/Sub 转发

5. Desktop B 收到消息:
   → 处理业务逻辑
   ← 回复 ack: { "type": "ack", "ackMsgId": "msg_001", "status": "ok" }

6. Gateway 收到 ack:
   → 从 PendingQueue 移除 msg_001
   → 完成投递
```
