# 14｜消息的三张面孔：磁盘上一张脸，网络上一张脸，屏幕上一张脸

> 这是 CatBuddy 技术专栏的第 14 篇。上篇讲了文件读写——Agent 怎么在一个可控的安全边界内读写用户文件，PathGuard 怎么画边界，`edit_file` 为什么坚持精确字符串替换。现在进入记忆系统——Agent 产生的所有内容怎么被存储、传输、渲染？这要先从一个看似小题大做的设计决策讲起：为什么同一条聊天消息要有三种不同的数据结构？

---

你有没有遇到过这种 bug：改了数据库的一个字段名，结果前端页面白屏了？

我有。而且不止一次。

CatBuddy 早期犯过一个典型的错误——存储层用了一套类型，UI 层直接用这同一套类型渲染。开发初期没什么问题，直到有一天我们给 `MessageRecord` 加了个 `reasoningContent` 字段（DeepSeek 的推理内容），Web 端突然不显示消息了。

追踪了两小时，原因很简单：`MessageRecord` 的字段名是 `snake_case`（`tool_call_id`），但 Web 端通过 WebSocket 收到的 JSON 是 `camelCase`（`toolCallId`）。只有一个转换函数没更新。

根因：**同一套类型承载了三个不同场景的需求，改一处惊动全身**。

后来的重构方案就是这篇文章要讲的——**三层消息类型**。

---

## 8.1 同一个你，三种场合三种打扮

用个生活比喻。

你在家穿睡衣，出门穿便装，面试穿正装。都是你，但不同场合需要不同的形态。

CatBuddy 的消息也一样——同一条"你好，请帮我重构这个文件"，在不同的系统环节表现为完全不同的数据结构：

| 环节 | 数据结构 | 比喻 |
|------|----------|------|
| 存磁盘 | `MessageRecord` | 在家——舒服就行，不用化妆 |
| 网络传输 | `WebuiThreadPersistedPayload` | 出门——整齐干净，信息完整但不冗余 |
| 屏幕渲染 | `UIMessage` | 面试——精心打扮，加了很多装饰 |

为什么不能用一个数据结构走天下？

---

## 8.2 MessageRecord：为磁盘而生

`MessageRecord` 存的是 JSONL 文件——每行一条消息。它的设计目标只有一个：**读回来的时候能完整还原 Agent 的思考过程**。

```typescript
interface MessageRecord {
  id: number                    // 自增序号，JSONL 行号
  sessionKey: string            // 属于哪个会话
  role: 'user' | 'assistant' | 'tool' | 'system'
  content: string               // 消息正文
  toolCalls?: ToolCallRequest[] // assistant 调用了哪些工具
  toolCallId?: string           // tool 结果对应哪个调用
  name?: string                 // tool 结果对应哪个工具名
  reasoningContent?: string     // DeepSeek 推理过程
  timestamp: string             // ISO 时间戳
  tokenUsage?: TokenUsage       // token 消耗
  latencyMs?: number            // 响应耗时
}
```

它的特点：

**1. 字段名是 snake_case**

`toolCallId`（驼峰）在 JSONL 里是 `tool_call_id`（蛇形）。不是风格偏好——JSONL 是纯文本，其他工具（`cat`、`grep`、`jq`）可能直接操作它。`snake_case` 被更广泛地用在命令行工具和数据管道中。

**2. 没有任何 UI 相关字段**

没有 `isStreaming`、没有 `toolProgress`、没有 `fileEdits`。这些是渲染层的事，磁盘不需要关心"这条消息是不是正在流式输出"。

**3. 笨重但完整**

每个 `MessageRecord` 都带着 `sessionKey`，这意味着即使你把 JSONL 文件单独拿出来，也能追溯到它属于哪个会话。对于调试和数据恢复，这很关键。

---

## 8.3 WebuiThreadPersistedPayload：为网络而生

当 Web 端（或手机端）请求"给我这个会话的历史消息"，CatBuddy 不会直接把 JSONL 原始内容发过去。它会通过 `buildWebuiThreadPayload()` 转换成一个传输专用的格式：

```typescript
interface WebuiThreadPersistedPayload {
  schemaVersion: number        // 版本号，用于兼容性
  sessionKey: string           // 会话标识
  savedAt: string              // 保存时间
  messages: UIMessage[]        // 已经是 UI 就绪的消息列表
}
```

传输层做了三件事：

**1. 字段名全部转 camelCase**

这是 JSON 世界的惯例。`tool_call_id` → `toolCallId`。

**2. 聚合 tool 调用**

JSONL 里一个 assistant 消息 + 三个 tool 结果消息 = 4 行。传输层把它们聚合为一个 `UIMessage`（kind: 'trace'），附带一个 `toolProgress` 对象——把"开始调用"和"调用完成"合并到同一个条目里。

**3. 合成文件编辑事件**

`write_file` 和 `edit_file` 的调用，不会单独传一条"文件已修改"的 WebSocket 消息。传输层从 tool 调用历史和结果中**反向合成**出 `FileEditEvent[]`——前端拿到后直接渲染文件变更列表。

---

## 8.4 UIMessage：为 React 而生

到了渲染层，消息类型变得"花哨"起来：

```typescript
interface UIMessage {
  id: string
  role: Role
  content: string
  kind?: 'message' | 'trace'   // 普通消息 vs 工具调用组
  isStreaming?: boolean         // 正在流式输出？
  toolProgress?: Record<string, ToolProgressEvent>  // 工具执行进度
  fileEdits?: UIFileEdit[]     // 文件变更列表
  activitySegmentId?: string   // 同组折叠
  reasoning?: string           // DeepSeek 推理过程
  reasoningStreaming?: boolean // 推理是否在流式输出
  latencyMs?: number           // 响应耗时
  tokenUsage?: TokenUsage      // token 消耗
}
```

这些字段在 MessageRecord 里全部不存在：

- **`isStreaming`**：磁盘不需要知道"这条消息还没写完"，但 React 需要——它决定了消息气泡是否展示闪烁光标。
- **`toolProgress`**：一个按 `callId` 聚合的进度对象。"读文件"开始 → "读文件"完成，在 UI 上显示为同一个条目的状态变化，而不是两条独立消息。
- **`activitySegmentId`**：一组相关的工具调用（assistant 的一次"干活"轮次）折叠在一个可展开的区块里。
- **`fileEdits`**：从工具调用历史中合成出的文件变更列表。"写了3个文件，修改了1个"——前端直接渲染，不用自己去解析。

## 8.5 buildWebuiThreadPayload()：唯一的转换汇聚点

整个转换逻辑只有一个入口函数：`buildWebuiThreadPayload()`。

它从 `MessageRecord[]`（JSONL 数据）到 `UIMessage[]`（UI 就绪数据），大概 250 行代码。

为什么要求"唯一"？因为每多一个转换路径，就多一个"字段没同步"的风险。CatBuddy 经历过那个阶段——IPC 层手拼 UIMessage、Gateway 层又手拼一次、WebSocket 推送时再手拼一次。三个地方拼，三个地方不同步。

现在的规则很简单：**如果你想从 MessageRecord 生成 UIMessage，只能用 `buildWebuiThreadPayload()`，没有第二个函数**。

转换逻辑的核心：

```
遍历 MessageRecord[]
  │
  ├── role === 'assistant' && 有 toolCalls
  │   ├── 收集所有后续的 tool 结果消息
  │   ├── 合成 toolProgress（start → end 合并）
  │   ├── 合成 fileEdits（从 write_file/edit_file 调用中提取）
  │   └── 生成 1 条 trace UIMessage（可折叠的工具调用组）
  │
  ├── role === 'user' / 'assistant' / 'system'
  │   └── 生成 1 条 message UIMessage
  │
  └── role === 'tool'（孤立的工具结果，无对应 assistant）
      └── 同上，生成 trace UIMessage
```

反向转换也存在：`sessionRecordsFromWebuiMessages()`——当用户编辑了一条消息（重新发送），UI 层的 UIMessage 需要转回 MessageRecord 存盘。这个函数同样只有一个。

## 8.6 WebSocket 流式推送：第三张脸之外

上面讲的是"历史消息回放"的路径。但 CatBuddy 还有一个路径——**实时流式推送**。

当 Agent 正在运行，LLM 在流式输出时，消息不是"一次性发完"的。它是这样推的：

```
WebSocket 帧类型：

reasoning_delta   → "嗯，用户想要重构这个文件..."     (DeepSeek 推理)
content_delta     → "我来看看..."                      (正文流式)
tool_progress     → { name: "read_file", phase: "start" }
tool_progress     → { name: "read_file", phase: "end", detail: "..." }
file_edit         → { path: "src/index.ts", status: "editing" }
content_delta     → "重构完成"                          (继续正文)
turn_end          → { latencyMs: 3420, tokenUsage: {...} }
```

前端有一个 `StreamBuffer` 负责把这些增量帧拼成 `UIMessage`。它的逻辑：

- 每个 `content_delta` → 追加到当前 assistant 消息的 `content`，`isStreaming: true`
- `reasoning_delta` → 追加到 `reasoning`，`reasoningStreaming: true`
- `tool_progress` start → 插入一个新的 tool 条目到 `toolProgress`
- `tool_progress` end → 更新同一条目的 phase
- `turn_end` → `isStreaming: false`，消息完成

这套机制让用户体验到"一个完整的 Agent 思考过程"，而不是"等 30 秒后一次性出现结果"。

## 如果重来一次

三层类型的设计方向是对的，但实现上有一个遗憾：`WebuiThreadPersistedPayload` 和 `UIMessage` 的边界有点模糊。理想情况下，传输层应该是一个纯粹的数据容器，不包含 UI 概念（比如 `activitySegmentId` 和 `toolProgress` 的聚合逻辑）。但 `buildWebuiThreadPayload()` 里混入了大量的"UI 聚合"逻辑——把 4 条 tool 消息合并成 1 条 trace 消息。

更纯粹的做法可能是：传输层只负责格式转换（snake_case → camelCase），聚合逻辑放在前端的 `StreamBuffer` 或 React Hook 里。这样传输层更薄，各端的 UI 实现更自由。但考虑到性能（多个客户端不需要重复聚合），把聚合放在服务端也不算错——只是一个 trade-off。

---

> **这篇讲了什么？**
>
> 1. 同一条消息在 CatBuddy 里有三张"脸"：`MessageRecord`（磁盘存储，蛇形命名，只存必要字段）、`WebuiThreadPersistedPayload`（网络传输，驼峰命名，聚合工具调用）、`UIMessage`（UI 渲染，含 isStreaming/toolProgress/fileEdits 等渲染专用字段）。
> 2. 三层之间的转换只有一个汇聚点——`buildWebuiThreadPayload()`。禁止 IPC 层、Gateway 层各自手拼 UIMessage，所有转换走同一条路。
> 3. 实时流式推送走 WebSocket 增量帧，前端 StreamBuffer 把 `content_delta`、`tool_progress`、`file_edit` 等增量帧逐步拼成完整的 UIMessage。
