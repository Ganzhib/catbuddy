# 02｜三块积木：Desktop、Gateway、Web 怎么拼在一起

> 这是 CatBuddy 技术专栏的第 2 篇。上篇聊了 CatBuddy 想解决什么问题，这篇看它的三层架构——Desktop 负责跑 Agent 和操作文件，Gateway 做消息中继，Web 纯展示。以及：为什么一个桌面软件需要一个中间服务器？

---

CatBuddy 的功能需求横跨了三个世界——桌面的本地能力（Agent 运行、文件操作）、浏览器的跨设备触达（随时随地接入）、以及一个中继层让二者对话。这三个世界天然隔着一堵墙：浏览器不能读写本地文件，桌面程序没有公网 IP。

怎么把这三块拼在一起？

---

## 从"只有一个桌面 App"开始想

最直接的方案：CatBuddy 就是一个 Electron 桌面软件，安装、打开、用。Agent 在里面跑，文件在本地读，聊天记录存本地文件。简单、干净、不依赖任何外部服务。

这个方案能解决 **80% 的场景**：

- ✅ Agent 在你电脑上跑
- ✅ 文件操作在本地
- ✅ 你自己的 API Key
- ✅ 不依赖外部服务器

但它解决不了剩下的 **20%**——而这 20% 恰恰是 CatBuddy 区别于其他本地 AI 工具的关键。

那 **20% 是什么？**

**你离开电脑之后。** Agent 正在分析一个大型项目，还要跑 20 分钟。你合上笔记本，去楼下买咖啡。你想用手机看一眼进度——不行。Agent 锁在你的笔记本里。

**你在公司台式机上跑 Agent。** 回家后想在家里的笔记本上查看今天生成的分析报告。但 Agent 在公司内网机器上，你的笔记本连不上它。

**多设备共享一个 Agent。** 上午在工位 Mac 上讨论架构设计，下午在会议室 Windows 笔记本上想继续——聊天记录在 Mac 上，无缝接不上。

这些场景指向同一个需求：**Agent 的运行环境（Desktop）和用户的交互环境（UI）需要解耦。**

```
现状：Agent 和 UI 绑在同一台设备上
  ┌─────────────────────┐
  │      你的笔记本        │
  │  ┌──────┐ ┌────────┐ │
  │  │ Agent │ │  UI    │ │  ← 合上笔记本，全没了
  │  └──────┘ └────────┘ │
  └─────────────────────┘

目标：Agent 在一台设备上跑，UI 可以出现在任何设备上
  ┌──────────────┐          ┌──────────────┐
  │   台式机 (Agent) │◄──?──►│  手机/平板 (UI) │
  └──────────────┘          └──────────────┘
```

但"解耦"有一个硬伤：你的台式机没有公网 IP，手机没法直接连上它。你需要一个**双方都能访问的中间点**。

这就是 Gateway 存在的第一性原因——它不是一个"锦上添花"的功能，而是跨设备方案成立的前提条件。

---

## 三层架构全景图

有了上面的分析，系统骨架自然就出来了：

一句话总结三层关系：

> **Desktop 是大脑和双手，Web 是眼睛和嘴巴，Gateway 是神经系统。**

### Desktop：Agent 的"家"

Desktop 是一个 Electron 应用，它是整个系统里**唯一有"行动能力"**的一层。

核心进程叫 Agent Loop——一个持续运行的循环。负责接收用户输入、调用 LLM、根据 LLM 指示执行工具（读文件、跑命令）、把结果存到本地 JSONL 文件。

关键词：**本地**。文件在这里，API Key 在这里，Agent 的"生命"在这里。

### Web：纯展示和交互

Web 是一个标准 React 单页应用。它和 Desktop 共享同一套 UI 组件代码（`@catbuddy/ui` 包），但**不拥有任何本地能力**。

不能读文件、不能跑命令、不能调用 LLM。它唯一做的事：通过 Gateway 向 Desktop 发消息，然后把 Desktop 返回的东西渲染出来。

这种"有能力的不展示，有展示的没有能力"看起来反常识。但它是整个安全模型的基础——**暴露在公网的东西越少，越安全**。Web 可以部署在公网 CDN 上，但如果没有对应的 Desktop 在线，你打开了也什么都做不了。

### Gateway：只做"邮局"

Gateway 是一个 Fastify 服务器，整个系统里**唯一有公网地址**的一层。职责非常窄：

1. **用户鉴权**：邮箱验证码登录，签发 JWT
2. **设备配对**：Desktop 和 Web 用同一个邮箱登录后，Gateway 自动关联
3. **消息路由**：Web → Gateway → Desktop，Desktop → Gateway → Web
4. **会话缓存**：最近消息缓存在 MySQL 里，减少对 Desktop 的频繁请求

关键：**Gateway 不做 AI 推理、不存文件内容、不读你的代码。** 它就像邮局——经手你的信，但不拆开看。

## 一次远程对话，数据怎么流转的

假设你公司台式机上跑着 CatBuddy Desktop。你在地铁上掏出手机，打开 Web，发了条消息："帮我查一下 data_processor.py 里 `clean` 函数做了什么"。

```
                     数据闭环：一次远程文件分析请求
                     ════════════════════════════════

  ┌──────────┐          ┌──────────┐          ┌──────────────┐
  │ 你的手机   │  ① 消息  │ Gateway  │  ② 转发  │ 公司台式机     │
  │ (Web UI) │─────────►│          │─────────►│ (Desktop)    │
  │          │          │          │          │              │
  │          │          │          │          │ ③ Agent 收到请求│
  │          │          │          │          │   调用 LLM     │
  │          │          │          │          │   LLM 说:      │
  │          │          │          │          │   "我需要读     │
  │          │          │          │          │   data_processor│
  │          │          │          │          │   .py"         │
  │          │          │          │          │              │
  │          │          │          │          │ ④ Agent 读文件  │
  │          │          │   ⚠️     │          │ ┌───────────┐ │
  │          │          │ Gateway  │          │ │本地文件系统 │ │
  │          │          │ 看不见这个 │          │ │data_       │ │
  │          │          │ 文件内容   │          │ │processor.py│ │
  │          │          │          │          │ └───────────┘ │
  │          │          │          │          │              │
  │          │          │          │          │ ⑤ 把文件内容    │
  │          │          │          │          │   发给 LLM     │
  │          │          │          │          │   LLM 分析后    │
  │          │          │          │          │   生成回复      │
  │          │          │          │          │              │
  │          │  ⑦ 显示  │          │  ⑥ 回复  │              │
  │          │◄─────────│          │◄─────────│              │
  └──────────┘          └──────────┘          └──────────────┘

  关键事实：
  ┌────────────────────────────────────────────────────────────┐
  │ · data_processor.py 的完整内容从未离开过公司台式机             │
  │ · Gateway 只看到"有消息从 Web 到 Desktop"和"有回复回来"       │
  │ · LLM 服务商（Anthropic/OpenAI）看到了文件内容——但这取决于    │
  │   你用谁的 API Key。用 DeepSeek 还是 OpenAI，数据就去哪        │
  └────────────────────────────────────────────────────────────┘
```

每一步：

**①→②** 你在手机上发消息，Web 通过 WebSocket 发给 Gateway。Gateway 查了一下：这个 Web 连接对应的 Desktop 是谁——同一邮箱登录，Gateway 知道配对关系。

**③→④** Agent Loop 收到消息，发给 LLM。LLM 分析后说："我需要先看 data_processor.py 的内容。"

**④→⑤** Agent 调用本地 read_file 工具读取文件。文件在你台式机上，读取操作也在你台式机上。然后把内容作为新上下文发给 LLM。

**⑤→⑥** LLM 分析后生成回复："clean 函数的作用是对 DataFrame 执行以下操作：删除重复行、填充缺失值、标准化列名……"

**⑥→⑦** Agent 把回复存到本地 JSONL，同时通过 Gateway 推给手机。你的屏幕出现了分析结果。

**全程，data_processor.py 的内容没经过 Gateway 服务器，也没存在任何云端。**

## 如果不这样设计会怎样？

理解一个设计选择的最好方式，是看**不做这个选择会怎样**。

**方案 A：Desktop 直接暴露公网端口。** 台式机通常没有公网 IP。即使有，打开端口意味着安全攻击面急剧增大。每次 IP 变了（换 WiFi），手机就要重新配置连接地址。

**方案 B：Agent 跑在服务器上。** 文件需要上传到服务器——隐私合规归零。你的代码、数据库密码全在第三方服务器上。回到上一篇小陈的问题，对金融/医疗/军工来说不可接受。

**方案 C：只做桌面 App，放弃 Web。** 回到本节开头的问题——Agent 和 UI 绑定在单台设备，无法跨设备。

三层架构不是"最简洁的方案"，它是**在隐私、跨端、安全三个约束下，能找到的最简方案**。

## 技术选型一览

| 层 | 技术 | 为什么 |
|----|------|------|
| Desktop 壳 | **Electron** | 跨平台桌面能力 + 可直接复用 Web 层 React UI |
| Agent 引擎 | **Node.js**（Electron 主进程） | 原生文件系统/进程管理能力 |
| Gateway | **Fastify** | 高性能 HTTP + 原生 WebSocket，比 Express 快，比 Nest.js 轻 |
| Gateway DB | **MySQL** | 用户账号、会话元数据、设备配对——典型关系型数据 |
| Web UI | **React 18 + Vite** | 组件化 UI + 极致构建速度，UI 代码被 Desktop 和 Web 共享 |
| 全栈语言 | **TypeScript** | 三层共享类型定义，字段名拼错构建时就报错 |
| AI SDK | **Anthropic / OpenAI SDK** | 原生流式响应支持 |

每行的"为什么"都不是"这个技术最流行"，而是**"在这个架构下，它解决了哪个具体问题"**。

---

> **这篇讲了什么？**
>
> 1. CatBuddy 三层架构：Desktop（Agent+文件）→ Gateway（消息中继+鉴权）→ Web（纯UI）。
> 2. Gateway 不是锦上添花——没有它，跨设备方案就不成立。但它不做 AI，不存文件，只是个邮局。
> 3. 数据闭环核心：文件操作永远在 Desktop 本地。一次远程分析请求的全流程中，源代码从未经过 Gateway。
