# 04｜Agent 内容引擎：整个系统的灵魂

> 这是 CatBuddy 技术专栏的第 4 篇。前三篇讲了为什么存在、三层物理架构、12 个包怎么组织。这篇进入最核心的概念——"Agent 内容引擎"。这六个字会反复出现，所以先掰开揉碎讲清楚。

---

很多人第一次听说"AI Agent"，脑子里浮现的是一个聊天窗口——你打字，它回复。交互形式确实是聊天。但如果 CatBuddy 只是一个套了 Electron 壳的 ChatGPT 客户端，那它不值得写 21 篇文章。

Agent 和"聊天机器人"的差别，一个场景就能讲清楚。

**场景：你发了条消息"帮我分析一下这个项目的架构"。**

**聊天机器人**的做法：收到消息 → 发给 LLM → LLM 回复一段字 → 显示 → 结束。

**Agent（CatBuddy）**的做法：

1. 先不急着回复——用 `list_dir` 看看项目根目录有什么
2. 发现 `packages/` 和 `pnpm-workspace.yaml`——判断是 monorepo
3. 读 `pnpm-workspace.yaml`，知道有哪些包
4. 读几个关键 `package.json`，理解依赖关系
5. 读 `README.md` 和 `PROJECT_PLAN.md`，了解项目目的
6. 整合所有信息，生成架构分析报告
7. 顺手画成一张 Draw.io 架构图
8. 把报告和架构图一起显示
9. 保存这次对话的完整上下文——下次你问"具体讲讲 gateway 那层"，它能直接接上

看出区别了吗？

**聊天机器人是"一问一答"。Agent 是"一问 → 自主探索 → 多步操作 → 给出答案"。**

你不需要告诉 Agent 每一步做什么——它自己决定该读什么文件、该跑什么命令、该用什么方式呈现结果。你只需告诉它目标，它自己找路径。

### 身份一：状态机（大脑）——"现在该干什么"

Agent 内部有一个状态机，在几种状态间循环：

- **Idle**：等待用户输入
- **Thinking**：正在调 LLM，流式接收回复
- **Acting**：LLM 说"我需要读文件 X、执行命令 Y"，Agent 去执行
- **Saving**：把本轮结果写入本地聊天记录

为什么是状态机而不是简单函数调用？因为 **LLM 的回复不可预测**——有时一句话回答，有时连续调用七八个工具。函数调用无法优雅处理"连续多工具调用"，状态机可以。

> 📖 详细展开：第 5 篇

### 身份二：工具执行器（手脚）——能干什么

Agent 不能只"想"——要能操作文件、跑命令、查网页。这些能力通过 **MCP 协议（Model Context Protocol）** 接入。

MCP 像一个标准化插座：不管是文件系统工具、Shell 工具还是浏览器工具，只要实现了 MCP 协议，Agent 就能"插上就用"。工具执行结果作为新上下文喂回 LLM，让 LLM 基于真实信息继续推理。

> 📖 详细展开：第 6 篇

### 身份三：技能系统（技能包）——会做什么

MCP 给了 Agent "能读文件、能跑命令"的原子能力。但你要的不是原子能力——你要的是"帮我生成一个 PPT"。

Skill（技能包）做的事，是把 MCP 的原子能力组合成**有步骤、有提示词、有输出格式的完整工作流**。一个"PPT 生成"技能包含：理解需求 → 组织内容 → 生成文件 → 预览调整。

MCP 给了 Agent 手脚，Skill 教会了它一套组合拳。

> 📖 详细展开：第 7 篇

### 身份四：记忆系统——怎么被记住、传递、看到

Agent 不断产生内容——用户输入、LLM 回复、工具结果、中间状态。这些需要被：

- **持久化**（存磁盘，下次打开还在）→ 第 8、9 篇
- **传输**（跨 Gateway 从 Desktop 到 Web/手机）→ 第 11-14 篇
- **渲染**（变成屏幕上的消息气泡）→ 第 10、15 篇

三个环节形成完整信息流：Agent 产生内容 → 保存 → 传输 → 展示。任一环节格式不一致，链路就断。
