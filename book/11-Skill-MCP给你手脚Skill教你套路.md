# 10｜Skill：MCP 给你手脚，Skill 教你套路

> 这是 CatBuddy 技术专栏的第 10 篇。上篇讲了 MCP 协议——Agent 有了手脚，能读文件、跑命令、操作浏览器。但这只是"能干什么"，不是"会干什么"。这篇聊 Skill——怎么让 Agent 把原子工具组合成完整套路：做 PPT、处理 PDF、画架构图。

---

你第一次去健身房，教练给了你一堆器械：杠铃、哑铃、拉力器、跑步机。你每个都会用，但怎么练肱二头肌？先做什么、后做什么、每组几次、休息多久？

MCP 工具就是那堆器械。Skill 就是那张训练计划表。

MCP 给了 Agent "能读文件"、"能跑命令"、"能搜网页"。Skill 告诉它：**"要做 PPT？先理解需求→再组织内容→然后生成文件→最后预览调整。"**

---

## 7.1 Skill 和 MCP 工具到底差在哪？

用一个简单对比：

| | MCP 工具 | Skill |
|---|---|---|
| 粒度 | 原子操作 | 完整工作流 |
| 内容 | 函数签名 + 参数 Schema | 步骤 + 提示词 + 判断规则 |
| 谁定义 | 工具提供方（CatBuddy / 第三方） | Skill 作者（社区 / 你自己） |
| 比喻 | 螺丝刀、扳手 | 宜家安装说明书 |

举个例子——"生成 PPT"。

MCP 视角：你需要 `write_file`（写文件）、`exec`（跑命令）、`web_search`（找素材）。

Skill 视角：你收到一份 PPT Skill，打开 `SKILL.md` 文件，里面写着：

```markdown
# PPT 生成技能

## 步骤

1. 理解用户需求（主题、受众、页数）
2. 用 web_search 搜集相关素材
3. 组织大纲，逐页生成内容
4. 用 python-pptx 生成 .pptx 文件
5. 预览并接受修改意见

## 判断规则

- 如果用户说"做一个PPT"但没有指定页数 → 先追问
- 如果内容是技术主题 → 默认加入架构图页
```

Agent 不需要自己摸索"怎么做 PPT"——Skill 告诉它每一步该干嘛。

## 7.2 四级渐进式加载：不是所有技能都要全量灌进去

Skill 系统最核心的设计原则叫 **Progressive Disclosure（渐进式披露）**——Agent 的上下文窗口是有限的，不能把所有 Skill 的完整说明书一次性灌进去。CatBuddy 的做法是分四级加载：

```
第 1 级：摘要（name + description）       → 永远在上下文中
第 2 级：Always-on 正文                   → 永远在上下文中
第 3 级：按需读取 SKILL.md                → Agent 决定要用时自己读
第 4 级：捆绑资源（scripts/references/）    → 按需加载
```

### 第 1 级：摘要

每个 Skill 的 `SKILL.md` 都有 YAML frontmatter，包含 `name` 和 `description`。PromptBuilder 把所有非 always-on 的技能摘要拼成一个列表，注入到系统提示里：

```markdown
# Skills

以下技能可以扩展你的能力。需要使用某个技能时，用 read_file 读取它的 SKILL.md。

- **weather**: 获取当前天气和预报
- **diagram**: 分析代码生成架构图
- **cron**: 定时提醒和周期性任务
```

这一步只占几十个 token。Agent 知道"有哪些技能可用"，但不知道每个技能具体怎么用。

### 第 2 级：Always-on 技能

`memory` 和 `my` 两个技能被标记为 `always: true`。它们的完整 `SKILL.md` **永远在系统提示里**。

为什么？因为这两个技能太基础了——`memory` 让 Agent 记住跨会话的信息，`my` 让 Agent 能自查状态和配置。如果每次都要 Agent "先读说明书再用人格"，那用户的第一条消息就得等两轮。

### 第 3 级：按需读取

这是最巧妙的一层。普通技能的 `SKILL.md` **不在系统提示里**——Agent 只知道它们"存在"，不知道"怎么用"。当 Agent 判断需要某个技能时，它**自己用 `read_file` 去读 `SKILL.md`**。

比如你问"明天北京什么天气？"，Agent 的推理过程：

1. 看到 Skills 列表里有 `weather`
2. "用户要查天气，我应该用 weather 技能"
3. 调用 `read_file("skills/weather/SKILL.md")` —— 拿到完整说明书
4. 按说明书指示，调用 `curl wttr.in/Beijing` 获取天气数据
5. 格式化输出

这意味着：**你装了 20 个 Skill，Agent 的上下文里只有 20 行摘要 + 2 个 always-on 技能的正文**。每次只按需加载一个。Token 省下来了，响应速度自然更快。

### 第 4 级：捆绑资源

一个 Skill 文件夹的结构可能是这样的：

```
weather/
├── SKILL.md           ← 核心说明书（Agent 按需读取）
├── scripts/
│   └── fetch.py       ← 可执行脚本（Agent 用 exec 调用）
├── references/
│   └── api-doc.md     ← 参考文档（需要时再读）
└── assets/
    └── template.txt   ← 输出模板
```

`scripts/` 里的脚本可以被 Agent 直接用 `exec` 调用，`references/` 里的文档按需读取。这让 Skill 不仅仅是"一段提示词"，而是一个真正的**可执行包**。

## 7.3 CatBuddy 预置了哪些技能？

CatBuddy 的 Skill Marketplace 预置了 7 个精选技能：

| 技能 | 干什么的 | 类型 |
|------|----------|------|
| 🌤️ 天气查询 | 查天气和预报，无需 API Key | 一键启用 |
| 🎯 长期目标 | 拆解复杂任务，分阶段推进 | 一键启用 |
| ⏰ 定时提醒 | 设置一次性或周期性提醒 | 一键启用 |
| 📐 画架构图 | 分析代码生成 Draw.io 架构图 | 一键启用 |
| 🐙 GitHub | 管理仓库、Issue、PR、CI | 需配置 gh CLI |
| 🧾 链接摘要 | 总结网页、播客、本地文件 | 需配置 summarize CLI |
| 🖥️ tmux 终端 | 远程控制 tmux 会话 | 需系统安装 tmux |

另外，`skill-creator` 是一个特殊的技能——它教你**怎么创建新的 Skill**。你用 CatBuddy 跟它说"我想做一个自动发邮件的技能"，它会引导你一步步创建 `SKILL.md`、写 `scripts/`、打包。这是一个"元技能"。

## 7.4 安装和热更新：下一条消息就能用

Skill 的安装流程简单到令人发指：

1. 用户在 UI 里点"安装"
2. CatBuddy 把 Skill 文件夹下载到工作区的 `skills/` 目录
3. 返回 `hotReload: true`
4. 系统提示的缓存失效（因为 Skill 目录的 mtime 变了）
5. 下一条消息，Agent 就能看到新 Skill 的摘要

没有重启，没有"刷新技能列表"按钮，不需要新开会话。因为 PromptBuilder 的缓存 key 包含了 Skill 目录的 mtime 指纹——文件变了，缓存自动失效。

禁用也一样：`disabledSkills` 变化 → 缓存失效 → 下条消息生效。

## 7.5 为什么不是"把所有 Skill 正文都灌进系统提示"？

你可能想问——既然 Skill 正文这么重要，为什么不全部塞进系统提示？这样 Agent 不用"先读说明书"就能直接用。

原因是 **token 经济学**。假设你有 10 个 Skill，每个 `SKILL.md` 平均 2000 token。全灌进去就是 20000 token——占到 Claude 标准上下文的 20%。你什么都没干，五分之一的"注意力"就被吃掉了。

而且Skill 越多，这个问题越严重。50 个 Skill 就是 10 万 token，直接爆掉。

按需读取的方案：10 个 Skill 的摘要大概 300 token，每次只加载一个 Skill 正文 2000 token。比你全灌进去省了 90·%。Agent 不是"不知道用什么技能"——摘要足够它判断。它只需要在执行前"看一眼说明书"。

## 如果重来一次

Skill 系统有一个遗憾：**Skill 之间的组合能力太弱**。目前每个 Skill 是独立的——Agent 一次只能按一个 Skill 的说明书操作。如果你想让 Agent 同时用"画架构图"和"链接摘要"两个技能协同工作，它需要自己判断怎么拼接。

理想情况下，Skill 应该声明"依赖其他 Skill"或"和 XX Skill 配合使用"。比如"长期目标"技能可以依赖"定时提醒"来拆解任务节点。但这个跨 Skill 编排能力目前还没做——你可以把它看成 CatBuddy 的 v2 路线图。

> **这篇讲了什么？**
>
> 1. MCP 工具是"螺丝刀和扳手"，Skill 是"宜家安装说明书"——一个提供原子操作，一个提供工作流和判断规则。
> 2. Skill 系统采用四级渐进式加载，核心是"按需读取"——摘要永远在上下文里，正文只在需要时才读。10 个 Skill 只占 300 token，而不是 20000。
> 3. 安装和禁用的热更新基于 mtime 指纹——文件变化自动触发缓存失效，下条消息即可使用，无需重启或新开会话。
