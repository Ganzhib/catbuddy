# 01｜为什么需要又一个 AI 编程助手？

> 这是 CatBuddy 技术专栏的第 1 篇。CatBuddy 是一个本地优先的 AI 编程助手——Agent 在你电脑上跑，API Key 你自己拿着，文件不出机器。这篇聊聊：Copilot、Cursor 已经很强了，为什么还要造轮子？

---

去年春天，我一个在银行做后端的朋友收到了安全部门的一封全员邮件：**禁止将任何包含业务逻辑的代码粘贴到外部 AI 工具。**

他的工作流瞬间瘫痪了。

这不只是银行的问题。医疗软件不能把患者数据给 AI，军工就不说了，连很多融到 B 轮的互联网创业公司，也开始关心"我们的核心算法到底有没有被上传到远方的服务器"。

与此同时，另一个场景同样真实：你用 Cursor 跑了个分析任务，半小时了，眼看快出结果——你合上笔记本去开会。到了会议室掏出手机，什么都看不了。你的 Agent 进度，锁在那台合上的 MacBook 里。

这些事让我开始认真想一个问题：**AI 编程助手，有没有第三条路？**

---

## 三个程序员的真实困境

不讲概念，讲三个场景。

### 场景一：代码不能出公司内网

小陈在一家金融科技公司负责支付模块。日常写 Go 和 Rust，代码仓库在内网 GitLab 上，连 GitHub 都访问不了。

他想用 AI 帮忙重构一段 2000 行的支付路由逻辑。但他不能把代码复制到 ChatGPT 网页——那是严重的合规事故。他也不能用 Copilot——虽然补全出现在 IDE 里，但推理请求同样要上传到 GitHub 的服务器。

对小陈来说，市面上所有 AI 编程工具都是"能看不能用"。

### 场景二：高铁上的断网时刻

小鹿是独立开发者，每周往返京沪。她在高铁上写代码——4 个半小时是难得的深度工作时间。

但高铁网络极其不稳。隧道断网、山区断网、甚至平原上也莫名其妙断网。Cursor 的 AI 补全时灵时不灵，更糟的是 Agent 模式正在帮她分析模块时断网了——进度全丢，重新来。

"我要的不是一个必须联网的工具，"小鹿说，"我要的是一个大部分时间在线、但断网也能继续干活的伙伴。"

### 场景三：电脑在家跑着，人在公司看着

阿杰让 Agent 帮他清洗数据、生成特征工程代码，预计要跑 40 分钟。但他必须离开工位去开评审会。

他不想干等。他想在会议室的平板上随时看进度。如果 Agent 报错了，他能在手机上发一句"重试"让它继续。

这要求 AI 助手不是"装在某台设备上的软件"，而是一个**你可以随时从任何设备接入的服务**。

---

三个场景指向同一个矛盾：

```
AI 推理能力越来越强
  ┃
  ┃  但是
  ┃
数据安全要求越来越严 × 网络环境越来越不可控 × 设备边界越来越模糊
```

传统的"AI = 云端大脑 + 本地编辑器"模型，在这三股力量下正在失效。

---

## 市面上的工具，各缺了什么

把主流 AI 编程工具捋一遍，大致三类，各有硬伤：

```
┌──────────────┬─────────────────┬─────────────────┬──────────────────┐
│              │   纯云端方案      │   IDE 插件方案    │   纯本地方案       │
│              │ (ChatGPT Web)   │ (Copilot/Cursor)│ (Ollama+Continue) │
├──────────────┼─────────────────┼─────────────────┼──────────────────┤
│ AI 在哪跑     │ 云端服务器       │ 云端服务器       │ 你的电脑上        │
│ 你的代码去哪了 │ 全上传          │ 上下文上传       │ 不出电脑          │
│ AI 能力强弱   │ ★★★★★ 最强      │ ★★★★★ 最强      │ ★★☆ 明显差距      │
│ 能不能操作文件 │ 不能            │ 部分能           │ 能               │
│ 能不能跨设备   │ 能（本来就是网页）│ 不能             │ 不能              │
│ 断网能不能用   │ 不能            │ 不能             │ 能               │
│ 安全合规       │ 基本不行         │ 看情况           │ 行               │
│ 硬伤          │ 数据全部离开机器  │ 核心推理依然上云  │ AI 不够聪明       │
└──────────────┴─────────────────┴─────────────────┴──────────────────┘
```

**纯云端**（ChatGPT、Claude 网页版）：代码复制粘贴的那一刻就已经不在你控制范围了。而且只能聊，不能主动读文件、跑命令。

**IDE 插件**（Copilot、Cursor）：看起来"像本地"——补全在编辑器里，Agent 能读项目文件。但一个关键事实很多人不知道：**推理还是在云端**。Cursor Agent 分析代码时，上下文会被发送到 Anthropic 或 OpenAI。大多数场景不是问题，但对小陈的金融科技公司来说，这就是红线。

**纯本地**（Ollama + Continue）：隐私做到了极致——模型在你 GPU 上跑，数据从未离开。但代价是模型能力差距明显。让一个 70 亿参数的开源模型重构支付系统核心逻辑——结果通常令人沮丧。

**三种方案，各有一个硬伤：云端不安全、插件不够本地、本地不够聪明。**

## 能不能三合一？

这就是 CatBuddy 想做的事。思路不是发明新技术，而是**重新排列已有的积木**：

```
         ┌──────────────────────────────────┐
         │        CatBuddy 的第三条路          │
         │                                  │
         │  用最强的云 AI（Claude/GPT）做推理    │  ← 云端方案的"强"
         │  Agent 和文件都在你的电脑上运行       │  ← 本地方案的"安全"
         │  一个轻量服务器帮你跨设备连接         │  ← 云方案的"跨端"
         │  API Key 你自己拿着                 │  ← 你的数据，你的账单
         └──────────────────────────────────┘
```

拆开来四层含义：

**一、Agent 跑在你自己的电脑上。** Agent 不只是聊天窗口，它是一个能主动执行任务的程序——读文件、理解目录结构、跑 Shell 命令、改代码。一切都在你电脑上发生，只有"需要 AI 推理的部分"才发出去。

**二、用你自己的 API Key。** CatBuddy 不自带模型，也不替你调用。你提供自己的 Anthropic / OpenAI / DeepSeek Key，推理请求从你的桌面端直接发给 AI 服务商。你可以随时换模型——用 Claude 分析架构、用 DeepSeek 写样板代码、用 GPT-4 做代码审查。

**三、跨设备通过一个"邮局"中转。** 中间放了一个轻量 Gateway 服务器，不做 AI 推理、不存文件内容、不读你的代码。它只做一件事：把消息从设备 A 转发到设备 B。就像邮局不拆你的信，只帮你投递。

**四、工作空间授权——Agent 不能乱翻你的硬盘。** 你每次打开新文件夹，必须在那文件夹根目录放一个 `.catbuddy` 文件，表示"我授权 Agent 在这个范围内工作"。没有这个文件，Agent 连文件夹里有几个文件都看不见。

## 这个专栏会聊什么

以上是"做什么"。但这不是产品说明书——这是一个**技术深度复盘专栏**。

你会看到的：

- **Agent 引擎到底怎么工作的**——不是调一次 API 就完事，而是状态机循环、工具调用、流式响应、错误恢复的完整链路
- **数据在系统内部怎么流转的**——从 LLM 吐出第一个 token，到你屏幕上出现那个字，中间经过了哪些模块、被转换了几次形态
- **跨设备协同怎么设计的**——一个"不做 AI"的邮局服务器，如何承载消息路由、用户鉴权、会话同步
- **工程决策背后的真实考量**——为什么选 JSONL 而不是 SQLite 存聊天记录？为什么把一个 1056 行的文件拆成 4 个模块？每一个选择都有它的故事

如果你正在设计自己的 AI Agent 产品，这个专栏可能帮你少踩很多坑。

如果只是对 AI 应用架构好奇——这里有 21 篇来自一线的真实经验。

> **这篇讲了什么？**
>
> 1. 现有 AI 编程工具分三类——纯云端（不安全）、IDE 插件（推理上云）、纯本地（不够聪明），各有硬伤。
> 2. CatBuddy 的解法：最强云 AI 做推理 + Agent 本地运行 + 自己持有 API Key + Gateway 跨端中继 + 工作空间沙箱。
> 3. 这个专栏将以 Agent 内容引擎为核心线索，从架构全景到每个模块细节，做一次完整的深度复盘。
