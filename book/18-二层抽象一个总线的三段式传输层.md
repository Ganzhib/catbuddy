# 17｜二层抽象一个总线的"三段式"传输层

> 这是 CatBuddy 技术专栏的第 17 篇。Desktop 里用 Electron IPC，Web 端用 WebSocket——但写完这行 `import { createAgentTransport } from "@catbuddy/client"` 后，上层代码再也不用关心底层是哪种通信方式。本文拆解这套"二层抽象 + 一个总线"的三段式传输层架构。

> **核心问题**：同一套 `useCatbuddyStream` → `catbuddyClient` 代码，怎么在 Electron 和浏览器里同时跑？传输层的可插拔接口是怎么设计的？

---

我们在前几篇讲完了流式渲染（第 10 篇）、上下文治理（第 11 篇）、命令系统（第 14 篇）。这些模块都运行在 Agent 端——主进程中。但用户看到的是**渲染进程**里的 UI，甚至是**远程浏览器**里的 UI。

Agent 端产生的 `delta`、`tool_progress`、`file_edit`、`turn_end` 事件，怎么跨越进程边界（甚至网络边界）到达 UI 层？这就是传输层要解决的问题。

CatBuddy 的答案不是"写一个 IPC 模块"或者"连接一个 WebSocket"。它是一个**两段抽象中间夹一个消息总线**的三段式架构：

```text
┌────────────────────────────────────────────────────────┐
│  UI Process (Renderer / Browser)                       │
│  ┌──────────────────────────────────────────────────┐  │
│  │  AgentTransport (interface)                      │  │
│  │  ├── IpcTransport    ← Electron preload bridge   │  │
│  │  ├── GatewayTransport ← Gateway Session WS       │  │
│  │  └── WsTransport     ← Direct WS (fallback)      │  │
│  └──────────────────────┬───────────────────────────┘  │
│                         │ IPC 或 WebSocket              │
│  ┌──────────────────────┴───────────────────────────┐  │
│  │  Main Process                                     │  │
│  │  ┌────────────────────────────────────────────┐  │  │
│  │  │  MessageBus (producer-consumer queue)       │  │  │
│  │  │  inbound:  Channel → AgentLoop              │  │  │
│  │  │  outbound: AgentLoop → Channel              │  │  │
│  │  └───────────────┬────────────────────────────┘  │  │
│  │                  │                                │  │
│  │  ┌───────────────┴────────────────────────────┐  │  │
│  │  │  BaseChannel (interface)                    │  │  │
│  │  │  ├── WebUIChannel   → Electron IPC events  │  │  │
│  │  │  └── GatewayChannel → Gateway WebSocket     │  │  │
│  │  └─────────────────────────────────────────────┘  │  │
│  └────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘
```

上层（AgentTransport）对上层消费者透明，下层（BaseChannel）对 Agent Loop 透明，中间的 MessageBus 把它们彻底解耦。下面逐层拆解。

---

## 17.1 AgentTransport：三选一，一行代码切换

如果把传输层比作水管，`AgentTransport` 就是水龙头的接口规格——不管你后面接的是铜管、PVC 管还是软管，拧上去的螺纹都是一样的。

```ts
// packages/shared/src/transport.ts
export interface AgentTransport {
  readonly kind: TransportKind  // 'ipc' | 'websocket'
  attach(callbacks: TransportCallbacks): () => void
  sendMessage(chatId: string, content: string, mediaUrls?: string[], workspaceFolderId?: string | null): void
  ensureSession?(chatId: string, workspaceFolderId?: string | null): void
  updateUrl?(url: string): void
}
```

只有两个必须实现的方法：`attach`（订阅事件）和 `sendMessage`（发送消息）。剩下的 `ensureSession` 和 `updateUrl` 是可选扩展——IPC 不需要这两个，但 Gateway 需要确保会话已同步到远端。

`TransportCallbacks` 则是传输层向上层的回调约定：

```ts
export interface TransportCallbacks {
  getActiveChatId: () => string
  onEvent: (ev: InboundEvent) => void
  onStatus: (status: ConnectionStatus) => void
  onSessionUpdate?: (chatId: string, scope?: SessionUpdateScope) => void
  onGoHome?: () => void
  onSendError?: (code: string) => void
}
```

注意这里的设计：传输层不关心 `InboundEvent` 是什么——它只是一个 `{ event: string, chat_id: string, ... }` 的 JSON 对象。传输层只负责"把这个对象从 A 点搬到 B 点"，不解析、不转换、不关心其业务含义。

### 17.1.1 工厂函数：自动检测模式

三种传输实现怎么选？不需要你手动判断。`createAgentTransport` 一行搞定：

```ts
// packages/client/src/transport/create-transport.ts
export function createAgentTransport(options: CreateTransportOptions): AgentTransport {
  const mode = options.mode === "auto" || !options.mode
    ? detectTransportMode()   // 自动检测
    : options.mode;

  if (mode === "desktop")  return new IpcTransport();
  if (mode === "gateway")  return new GatewayTransport({ httpBase, webToken: options.token });
  return new WsTransport(options.token, options.wsPath);
}

export function detectTransportMode(): "desktop" | "web" {
  return typeof window !== "undefined" && !!window.catbuddy ? "desktop" : "web";
}
```

核心判断逻辑只有一行：`!!window.catbuddy`。Electron 的 preload 脚本会把 IPC API 注入到 `window.catbuddy`，如果这个对象存在，说明运行在 Electron 渲染进程中；否则就是纯浏览器环境。

在浏览器环境下，进一步判断是走 Gateway（有 `httpBase`）还是直连 WebSocket。三种实现共用同一个接口，`catbuddyClient` 完全不感知差异。

### 17.1.2 IpcTransport：把 14 种 IPC 事件收敛成一个 `onEvent`

Electron IPC 的 API 是事件驱动的：主进程通过 `webContents.send(channel, payload)` 推送数据，渲染进程通过 `ipcRenderer.on(channel, handler)` 监听。

这导致了"频道爆炸"——CatBuddy 有 **14 种不同的 IPC 频道**：`stream-delta`、`stream-end`、`reasoning-delta`、`reasoning-end`、`tool-progress`、`file-edit`、`turn-complete`……每个频道一个回调函数，散布在代码各处。

`IpcTransport` 的工作就是把这些分散的频道**收敛成一个 `onEvent`**。通过一个通用的 `sub()` 辅助函数：

```ts
function sub<T extends { chatId?: string }>(
  subscribe: (cb: (data: T) => void) => (() => void) | undefined,
  mapper: (data: T, chatId: string) => InboundEvent,
  getActiveChatId: () => string,
  callbacks: TransportCallbacks,
): (() => void) | undefined {
  const unsub = subscribe((data) => {
    callbacks.onEvent(mapper(data, chatIdFromPayload(data, getActiveChatId)));
  });
  return unsub ?? undefined;
}
```

每种 IPC 频道只需要提供自己的 `mapper` 函数：

```ts
sub(api.onStreamDelta, (d, id) => ({ event: "delta", chat_id: id, text: d.content, stream_id: d.streamId }), ...),
sub(api.onReasoningDelta, (d, id) => ({ event: "reasoning_delta", chat_id: id, text: d.content }), ...),
sub(api.onStreamEnd, (d, id) => ({ event: "stream_end", chat_id: id, stream_id: d.streamId }), ...),
```

`onTurnComplete` 略微特殊——一个 IPC 事件产生两个 `InboundEvent`：

```ts
api.onTurnComplete((data) => {
  callbacks.onEvent({ event: "turn_end", chat_id, latency_ms, usage, tools_used });  // 第一帧
  callbacks.onEvent({ event: "goal_status", chat_id, status: "idle" });               // 第二帧
});
```

这种"一对多"映射是常见需求，`InboundEvent` 的扁平结构天然支持（不像某些框架要求一个事件只能产出一个对象）。

`attach()` 返回一个 cleanup 函数，遍历所有订阅的 unsubscribe 并依次调用——确保组件卸载时不会内存泄漏。

### 17.1.3 WsTransport：JSON InboundEvent 直接走 WebSocket

`WsTransport` 更简单——WebSocket 只监听一个 `message` 事件，收到的 JSON 直接 parse 成 `InboundEvent`：

```ts
this.socket.onmessage = (msg) => {
  const parsed = JSON.parse(String(msg.data));
  if (!isInboundEvent(parsed)) return;
  callbacks.onEvent(parsed);
  if (parsed.event === "session_updated") {
    callbacks.onSessionUpdate?.(parsed.chat_id, parsed.scope);
  }
};
```

但 WebSocket 有一个 IPC 不需要的额外职责：**断线重连**。`onclose` 时设置 2 秒重连定时器：

```ts
this.socket.onclose = () => {
  callbacks.onStatus("closed");
  this.scheduleReconnect(callbacks);  // 2s 后重试
};
```

重连状态通过 `callbacks.onStatus("reconnecting")` 通知上层，UI 层可以据此显示"重连中"提示。这种差异说明了一个设计原则：**传输层的实现可以各自处理自己的"脏活"（如重连），只要保持对外的 `AgentTransport` 接口不变。**

## 17.2 BaseChannel：Agent 端的对称抽象

如果说 `AgentTransport` 是 UI 端的"听筒"，`BaseChannel` 就是 Agent 端的"话筒"——对称地定义了 Agent 进程向外部发消息的约定：

```ts
// apps/desktop/src/main/channels/base.ts
export interface BaseChannel {
  readonly name: string;
  readonly displayName: string;
  start(): Promise<void>;
  stop(): Promise<void>;
  send(msg: OutboundMessage): Promise<void>;
  sendAssistantMessage?(chatId: string, text: string): Promise<void>;
  sendDelta?(chatId: string, delta: string): Promise<void>;
  sendStreamEnd?(chatId: string): Promise<void>;
  sendReasoningDelta?(chatId: string, delta: string): Promise<void>;
  sendReasoningEnd?(chatId: string): Promise<void>;
  sendToolProgress?(chatId: string, event: ToolEvent): Promise<void>;
  sendFileEdit?(chatId: string, edit: FileEditEvent): Promise<void>;
  sendDiagramEvent?(chatId: string, event: DiagramUiEvent): Promise<void>;
  sendTurnComplete?(chatId: string, data: TurnCompleteData): Promise<void>;
}
```

注意一个有趣的不对称性：`AgentTransport` 只暴露一个 `attach(callbacks)` → `onEvent`，把所有入站事件收敛成一个回调；而 `BaseChannel` 却细分为 9 种不同的 `send*()` 方法。

这不是设计不一致——这是**两队消费者的不同需求**。UI 层只需要知道"发生了某件事"，用一个 `switch(ev.event)` 就能分发到不同的 UI 更新逻辑；而 Agent 端需要精确控制每个事件的发送时机和格式，细分的 `sendDelta()`、`sendFileEdit()` 提供了类型化的参数约束，避免调用方传错字段。

### 17.2.1 GatewayChannel：同一套事件的三种路径

`GatewayChannel` 实现了 `BaseChannel`，但它做的事情比其他 Channel 多得多——它不仅是"把消息发出去"，还要管理远端连接、同步会话、转发远程用户的入站消息。

它的核心方法是 `emitSession()`：

```ts
private emitSession(chatId: string, event: Record<string, unknown>): void {
  this.gateway?.publishUiEvent(this.sessionKey(chatId), chatId, event);
}
```

所有 `sendDelta`、`sendToolProgress`、`sendFileEdit`……最终都走到这个私有方法。`publishUiEvent` 是 `GatewayDesktopClient` SDK 提供的方法——它负责把 `InboundEvent` 通过 Gateway 的 WebSocket 推送到远程浏览器。

更关键的是 `sendTurnComplete`——它不仅要推送事件，还要触发两个副作用：

```ts
async sendTurnComplete(chatId: string, data: TurnCompleteData): Promise<void> {
  this.emitSession(chatId, { event: "turn_end", ... });    // 推送 turn_end
  this.emitSession(chatId, { event: "goal_status", ... }); // 推送 goal_status
  this.gateway?.publishSessionsSync();                      // 同步会话列表
  this.gateway?.publishThreadSnapshot(this.sessionKey(chatId)); // 推送完整线程快照
}
```

因为 Web 端可能刚连接上，需要拿到最新一回合的完整消息历史。这是 Desktop-only 场景不需要考虑的"状态同步"问题。

## 17.3 MessageBus：解耦的中枢

现在有了 UI 端的 `AgentTransport` 和 Agent 端的 `BaseChannel`，但问题是：**Agent Loop 怎么知道该往哪个 Channel 发消息？Channel 怎么把用户的输入交给 Agent Loop？**

如果直接在 `AgentLoop` 里 `import WebUIChannel`，或者在 `IpcTransport` 里调用 `AgentLoop.send()`，那就形成了**双向耦合**——换一个 Channel 实现要改 AgentLoop 的代码，换一个 Transport 要改 Channel 的代码。

CatBuddy 的解法是：**消息总线（MessageBus）**。

```ts
// apps/desktop/src/main/bus/queue.ts
export class MessageBus {
  private _inbound: InboundMessage[] = [];
  private _outbound: OutboundMessage[] = [];
  private _inboundResolve: Resolver<InboundMessage> | null = null;
  private _outboundResolve: Resolver<OutboundMessage> | null = null;

  // Channel → AgentLoop
  publishInbound(msg: InboundMessage): void { ... }
  consumeInbound(timeoutMs = 1000): Promise<InboundMessage | null> { ... }

  // AgentLoop → Channel
  publishOutbound(msg: OutboundMessage): void { ... }
  consumeOutbound(timeoutMs = 1000): Promise<OutboundMessage | null> { ... }
}
```

这是一个**单消费者模式**的生产者-消费者队列。核心机制：

- **生产者**（Channel 或 AgentLoop）调用 `publish*` 放入消息
- **消费者**（AgentLoop 或 Channel）调用 `consume*` 取走消息
- 如果消费者正在等待（`_inboundResolve` 不为空），`publish` 直接 resolve 而不是入队
- 如果队列为空，`consume` 返回一个 Promise，等待超时（默认 1s）

这种设计的好处是：
1. **解耦**：AgentLoop 不知道 Channel 的存在，Channel 不知道 AgentLoop 的存在。它们都只认识 MessageBus。
2. **异步化**：AgentLoop 在消费入站消息时不是忙等，而是通过 `await bus.consumeInbound()` 异步等待。这让 Node.js 事件循环可以处理其他事情（如 IPC 事件回调）。
3. **超时兜底**：如果 1 秒内没有新消息，`consume` 返回 `null`，消费者可以决定是否继续等待。

把三段拼在一起，一次完整的消息往返是这样的：

```text
用户在浏览器输入 "帮我重构这个函数"

  浏览器: GatewayTransport.sendMessage(chatId, "帮我重构...")
      ↓ JSON WebSocket
  Gateway Server（转发）
      ↓
  主进程: GatewayChannel 收到入站消息
      ↓
  MessageBus.publishInbound({ chatId, content: "帮我重构..." })
      ↓ (Promise resolve)
  AgentLoop.consumeInbound() 拿到消息
      ↓
  AgentLoop.process() → AgentRunner.run() → LLM 推理 → 流式返回
      ↓
  MessageBus.publishOutbound({ event: "delta", chat_id, text: "好" })
      ↓ (Promise resolve)
  ChannelDispatcher 调用 GatewayChannel.sendDelta(chatId, "好")
      ↓ Gateway WebSocket
  浏览器: GatewayTransport 收到 "message" 事件
      ↓
  callbacks.onEvent({ event: "delta", chat_id, text: "好" })
      ↓
  useCatbuddyStream → StreamBuffer → React setState → 页面渲染 "好"
```

整个过程，Agent Loop 的代码里没有任何 `ipcMain`、`BrowserWindow` 或 `WebSocket` 的引用。它只对 `MessageBus` 说话。

## 17.4 总结

> **这篇讲了什么？**
>
> 1. CatBuddy 的传输层是"二层抽象一个总线"的三段式架构：`AgentTransport` 接口对 UI 端提供可插拔的事件订阅（三种实现：IPC / Gateway WS / 直连 WS），`BaseChannel` 接口对 Agent 端提供类型化的消息发送（WebUIChannel / GatewayChannel），`MessageBus` 作为生产者-消费者队列把两端彻底解耦。
> 2. `createAgentTransport()` 工厂函数通过 `!!window.catbuddy` 自动检测运行环境，一行代码切换传输模式。上层 `catbuddyClient` 完全不感知底层是 IPC 还是 WebSocket。
> 3. 两端的接口设计有不对称性——UI 端收敛为单一 `onEvent` 回调（方便 `switch` 分发），Agent 端细分为 9 种 `send*()` 方法（类型化参数约束）——这是不同消费者的真实需求决定的，不是设计不一致。
