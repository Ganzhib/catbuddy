# 18｜二层抽象一个总线的"三段式"传输层

> 这是 CatBuddy 技术专栏的第 18 篇。上篇讲了双重存储——JSONL 文件 × MySQL 缓存怎么协同，"文件即数据库"的哲学到底是什么意思。这篇切换到通信层——Desktop 里用 Electron IPC，Web 端用 WebSocket——但写完这行 `import { createAgentTransport } from "@catbuddy/client"` 后，上层代码再也不用关心底层是哪种通信方式。本文拆解这套"二层抽象 + 一个总线"的三段式传输层架构。

> **核心问题**：同一套 `useCatbuddyStream` → `catbuddyClient` 代码，怎么在 Electron 和浏览器里同时跑？传输层的可插拔接口是怎么设计的？

---

我们在前几篇讲完了流式渲染（第 10 篇）、上下文治理（第 11 篇）、命令系统（第 14 篇）。这些模块都运行在 Agent 端——主进程中。但用户看到的是**渲染进程**里的 UI，甚至是**远程浏览器**里的 UI。

Agent 端产生的 `delta`、`tool_progress`、`file_edit`、`turn_end` 事件，怎么跨越进程边界（甚至网络边界）到达 UI 层？这就是传输层要解决的问题。

CatBuddy 的答案不是"写一个 IPC 模块"或者"连接一个 WebSocket"。它是一个**两段抽象中间夹一个消息总线**的三段式架构：

```text
┌────────────────────────────────────────────────────────┐
│  UI Process (Renderer / Browser)                       │
│  ┌──────────────────────────────────────────────────┐  │
│  │  AgentTransport (interface)                      │  │
│  │  ├── IpcTransport    ← Electron preload bridge   │  │
│  │  ├── GatewayTransport ← Gateway Session WS       │  │
│  │  └── WsTransport     ← Direct WS (fallback)      │  │
│  └──────────────────────┬───────────────────────────┘  │
│                         │ IPC 或 WebSocket              │
│  ┌──────────────────────┴───────────────────────────┐  │
│  │  Main Process                                     │  │
│  │  ┌────────────────────────────────────────────┐  │  │
│  │  │  MessageBus (producer-consumer queue)       │  │  │
│  │  │  inbound:  Channel → AgentLoop              │  │  │
│  │  │  outbound: AgentLoop → Channel              │  │  │
│  │  └───────────────┬────────────────────────────┘  │  │
│  │                  │                                │  │
│  │  ┌───────────────┴────────────────────────────┐  │  │
│  │  │  BaseChannel (interface)                    │  │  │
│  │  │  ├── WebUIChannel   → Electron IPC events  │  │  │
│  │  │  └── GatewayChannel → Gateway WebSocket     │  │  │
│  │  └─────────────────────────────────────────────┘  │  │
│  └────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘
```

上层（AgentTransport）对上层消费者透明，下层（BaseChannel）对 Agent Loop 透明，中间的 MessageBus 把它们彻底解耦。下面逐层拆解。

---

## 17.1 AgentTransport：三选一，一行代码切换

如果把传输层比作水管，`AgentTransport` 就是水龙头的接口规格——不管你后面接的是铜管、PVC 管还是软管，拧上去的螺纹都是一样的。

```ts
// packages/shared/src/transport.ts
export interface AgentTransport {
  readonly kind: TransportKind  // 'ipc' | 'websocket'
  attach(callbacks: TransportCallbacks): () => void
  sendMessage(chatId: string, content: string, mediaUrls?: string[], workspaceFolderId?: string | null): void
  ensureSession?(chatId: string, workspaceFolderId?: string | null): void
  updateUrl?(url: string): void
}
```

只有两个必须实现的方法：`attach`（订阅事件）和 `sendMessage`（发送消息）。剩下的 `ensureSession` 和 `updateUrl` 是可选扩展——IPC 不需要这两个，但 Gateway 需要确保会话已同步到远端。

`TransportCallbacks` 则是传输层向上层的回调约定：

```ts
export interface TransportCallbacks {
  getActiveChatId: () => string
  onEvent: (ev: InboundEvent) => void
  onStatus: (status: ConnectionStatus) => void
  onSessionUpdate?: (chatId: string, scope?: SessionUpdateScope) => void
  onGoHome?: () => void
  onSendError?: (code: string) => void
}
```

注意这里的设计：传输层不关心 `InboundEvent` 是什么——它只是一个 `{ event: string, chat_id: string, ... }` 的 JSON 对象。传输层只负责"把这个对象从 A 点搬到 B 点"，不解析、不转换、不关心其业务含义。

### 17.1.1 工厂函数：自动检测模式

三种传输实现怎么选？不需要你手动判断。`createAgentTransport` 一行搞定：

```ts
// packages/client/src/transport/create-transport.ts
export function createAgentTransport(options: CreateTransportOptions): AgentTransport {
  const mode = options.mode === "auto" || !options.mode
    ? detectTransportMode()   // 自动检测
    : options.mode;

  if (mode === "desktop")  return new IpcTransport();
  if (mode === "gateway")  return new GatewayTransport({ httpBase, webToken: options.token });
  return new WsTransport(options.token, options.wsPath);
}

export function detectTransportMode(): "desktop" | "web" {
  return typeof window !== "undefined" && !!window.catbuddy ? "desktop" : "web";
}
```

核心判断逻辑只有一行：`!!window.catbuddy`。Electron 的 preload 脚本会把 IPC API 注入到 `window.catbuddy`，如果这个对象存在，说明运行在 Electron 渲染进程中；否则就是纯浏览器环境。

在浏览器环境下，进一步判断是走 Gateway（有 `httpBase`）还是直连 WebSocket。三种实现共用同一个接口，`catbuddyClient` 完全不感知差异。

### 17.1.2 IpcTransport：把 14 种 IPC 事件收敛成一个 `onEvent`

Electron IPC 的 API 是事件驱动的：主进程通过 `webContents.send(channel, payload)` 推送数据，渲染进程通过 `ipcRenderer.on(channel, handler)` 监听。

这导致了"频道爆炸"——CatBuddy 有 **14 种不同的 IPC 频道**：`stream-delta`、`stream-end`、`reasoning-delta`、`reasoning-end`、`tool-progress`、`file-edit`、`turn-complete`……每个频道一个回调函数，散布在代码各处。

`IpcTransport` 的工作就是把这些分散的频道**收敛成一个 `onEvent`**。通过一个通用的 `sub()` 辅助函数：

```ts
function sub<T extends { chatId?: string }>(
  subscribe: (cb: (data: T) => void) => (() => void) | undefined,
  mapper: (data: T, chatId: string) => InboundEvent,
  getActiveChatId: () => string,
  callbacks: TransportCallbacks,
): (() => void) | undefined {
  const unsub = subscribe((data) => {
    callbacks.onEvent(mapper(data, chatIdFromPayload(data, getActiveChatId)));
  });
  return unsub ?? undefined;
}
```

每种 IPC 频道只需要提供自己的 `mapper` 函数：

```ts
sub(api.onStreamDelta, (d, id) => ({ event: "delta", chat_id: id, text: d.content, stream_id: d.streamId }), ...),
sub(api.onReasoningDelta, (d, id) => ({ event: "reasoning_delta", chat_id: id, text: d.content }), ...),
sub(api.onStreamEnd, (d, id) => ({ event: "stream_end", chat_id: id, stream_id: d.streamId }), ...),
```

`onTurnComplete` 略微特殊——一个 IPC 事件产生两个 `InboundEvent`：

```ts
api.onTurnComplete((data) => {
  callbacks.onEvent({ event: "turn_end", chat_id, latency_ms, usage, tools_used });  // 第一帧
  callbacks.onEvent({ event: "goal_status", chat_id, status: "idle" });               // 第二帧
});
```

这种"一对多"映射是常见需求，`InboundEvent` 的扁平结构天然支持（不像某些框架要求一个事件只能产出一个对象）。

`attach()` 返回一个 cleanup 函数，遍历所有订阅的 unsubscribe 并依次调用——确保组件卸载时不会内存泄漏。

### 17.1.3 WsTransport：JSON InboundEvent 直接走 WebSocket

`WsTransport` 更简单——WebSocket 只监听一个 `message` 事件，收到的 JSON 直接 parse 成 `InboundEvent`：

```ts
this.socket.onmessage = (msg) => {
  const parsed = JSON.parse(String(msg.data));
  if (!isInboundEvent(parsed)) return;
  callbacks.onEvent(parsed);
  if (parsed.event === "session_updated") {
    callbacks.onSessionUpdate?.(parsed.chat_id, parsed.scope);
  }
};
```

但 WebSocket 有一个 IPC 不需要的额外职责：**断线重连**。`onclose` 时设置 2 秒重连定时器：

```ts
this.socket.onclose = () => {
  callbacks.onStatus("closed");
  this.scheduleReconnect(callbacks);  // 2s 后重试
};
```

重连状态通过 `callbacks.onStatus("reconnecting")` 通知上层，UI 层可以据此显示"重连中"提示。这种差异说明了一个设计原则：**传输层的实现可以各自处理自己的"脏活"（如重连），只要保持对外的 `AgentTransport` 接口不变。**

## 17.2 BaseChannel：Agent 端的对称抽象

如果说 `AgentTransport` 是 UI 端的"听筒"，`BaseChannel` 就是 Agent 端的"话筒"——对称地定义了 Agent 进程向外部发消息的约定：

```ts
// apps/desktop/src/main/channels/base.ts
export interface BaseChannel {
  readonly name: string;
  readonly displayName: string;
  start(): Promise<void>;
  stop(): Promise<void>;
  send(msg: OutboundMessage): Promise<void>;
  sendAssistantMessage?(chatId: string, text: string): Promise<void>;
  sendDelta?(chatId: string, delta: string): Promise<void>;
  sendStreamEnd?(chatId: string): Promise<void>;
  sendReasoningDelta?(chatId: string, delta: string): Promise<void>;
  sendReasoningEnd?(chatId: string): Promise<void>;
  sendToolProgress?(chatId: string, event: ToolEvent): Promise<void>;
  sendFileEdit?(chatId: string, edit: FileEditEvent): Promise<void>;
  sendDiagramEvent?(chatId: string, event: DiagramUiEvent): Promise<void>;
  sendTurnComplete?(chatId: string, data: TurnCompleteData): Promise<void>;
}
```

注意一个有趣的不对称性：`AgentTransport` 只暴露一个 `attach(callbacks)` → `onEvent`，把所有入站事件收敛成一个回调；而 `BaseChannel` 却细分为 9 种不同的 `send*()` 方法。

这不是设计不一致——这是**两队消费者的不同需求**。UI 层只需要知道"发生了某件事"，用一个 `switch(ev.event)` 就能分发到不同的 UI 更新逻辑；而 Agent 端需要精确控制每个事件的发送时机和格式，细分的 `sendDelta()`、`sendFileEdit()` 提供了类型化的参数约束，避免调用方传错字段。

### 17.2.1 GatewayChannel：同一套事件的三种路径

`GatewayChannel` 实现了 `BaseChannel`，但它做的事情比其他 Channel 多得多——它不仅是"把消息发出去"，还要管理远端连接、同步会话、转发远程用户的入站消息。

它的核心方法是 `emitSession()`：

```ts
private emitSession(chatId: string, event: Record<string, unknown>): void {
  this.gateway?.publishUiEvent(this.sessionKey(chatId), chatId, event);
}
```

所有 `sendDelta`、`sendToolProgress`、`sendFileEdit`……最终都走到这个私有方法。`publishUiEvent` 是 `GatewayDesktopClient` SDK 提供的方法——它负责把 `InboundEvent` 通过 Gateway 的 WebSocket 推送到远程浏览器。

更关键的是 `sendTurnComplete`——它不仅要推送事件，还要触发两个副作用：

```ts
async sendTurnComplete(chatId: string, data: TurnCompleteData): Promise<void> {
  this.emitSession(chatId, { event: "turn_end", ... });    // 推送 turn_end
  this.emitSession(chatId, { event: "goal_status", ... }); // 推送 goal_status
  this.gateway?.publishSessionsSync();                      // 同步会话列表
  this.gateway?.publishThreadSnapshot(this.sessionKey(chatId)); // 推送完整线程快照
}
```

因为 Web 端可能刚连接上，需要拿到最新一回合的完整消息历史。这是 Desktop-only 场景不需要考虑的"状态同步"问题。

## 17.3 MessageBus：整个系统的"脊椎神经"

现在有了 UI 端的 `AgentTransport` 和 Agent 端的 `BaseChannel`，但问题是：**Agent Loop 怎么知道该往哪个 Channel 发消息？Channel 怎么把用户的输入交给 Agent Loop？**

如果直接在 `AgentLoop` 里 `import WebUIChannel`，或者在 `IpcTransport` 里调用 `AgentLoop.send()`，那就形成了**双向耦合**——换一个 Channel 实现要改 AgentLoop 的代码，换一个 Transport 要改 Channel 的代码。

CatBuddy 的解法是：**消息总线（MessageBus）**。它不是一个简单的 pub/sub 工具，而是 CatBuddy 整个进程的**脊椎神经**——所有信息流都经过它，所有模块都通过它通信，但没有任何模块直接知道彼此的存在。

先看完整实现。它只有 **97 行**：

```ts
// apps/desktop/src/main/bus/queue.ts（完整代码）
type Resolver<T> = (msg: T) => void;

export class MessageBus {
  private _inbound: InboundMessage[] = [];
  private _outbound: OutboundMessage[] = [];
  private _inboundResolve: Resolver<InboundMessage> | null = null;
  private _outboundResolve: Resolver<OutboundMessage> | null = null;
  private _running = false;

  // ═══ Inbound（通道 → Agent） ═══
  publishInbound(msg: InboundMessage): void {
    if (this._inboundResolve) {
      this._inboundResolve(msg);      // 有人在等，直接交付
      this._inboundResolve = null;
    } else {
      this._inbound.push(msg);        // 没人在等，先排队
    }
  }

  consumeInbound(timeoutMs = 1000): Promise<InboundMessage | null> {
    if (this._inbound.length > 0) {
      return Promise.resolve(this._inbound.shift()!);  // 队列有货，直接拿
    }
    let timer: NodeJS.Timeout;
    return new Promise<InboundMessage | null>((resolve) => {
      this._inboundResolve = resolve;                   // 注册等待者
      timer = setTimeout(() => {
        if (this._inboundResolve === resolve) {
          this._inboundResolve = null;
          resolve(null);                                // 超时返 null
        }
      }, timeoutMs);
    }).finally(() => clearTimeout(timer));
  }

  // Outbound 方向完全对称，结构相同，略
}
```

97 行代码，两个方向完全对称。但这 97 行承载了 CatBuddy 全部的消息流转。下面逐层拆解它的设计。

### 17.3.1 为什么不是 EventEmitter？

看到"消息总线"四个字，你的第一反应可能是 Node.js 的 `EventEmitter`——`bus.on('message', handler)`，谁关心谁订阅。这确实是最常见的"总线"实现：

```ts
// 常见但 CatBuddy 没选的做法
class NaiveBus extends EventEmitter {
  send(msg) { this.emit('message', msg); }
}
// AgentLoop: bus.on('message', handler)
// Channel:   bus.on('message', handler)
```

但如果用 EventEmitter，你有三个问题：

1. **多个订阅者难以协调。** 入站消息来了，AgentLoop 和 Channel 都收到了——但消息应该只被 AgentLoop **消费一次**。谁负责"消费后删除"？EventEmitter 不提供这个语义。

2. **背压无处安放。** 如果 AgentLoop 正在处理一个长任务（LLM 推理跑了两分钟），期间用户发了 5 条消息。EventEmitter 没有任何排队和等待机制——消息要么在回调里堆积，要么丢失。

3. **"等待者"模式无法实现。** CatBuddy 的核心循环是 `while(running) { const msg = await bus.consumeInbound(); process(msg); }`——这是一个阻塞式消费者，AgentLoop 的生命就是"等消息→处理→再等消息"。EventEmitter 的 `on('message', cb)` 每次触发都执行 callback，无法表达"我在等，给我下一个"的语义。

CatBuddy 选择的是一个**单消费者阻塞队列**——参考了原版 Python 项目中 `catbuddy/bus/queue.py` 的实现。每个方向（inbound / outbound）都只有一个消费者：

| 方向 | 消费者 | 它做什么 |
|------|--------|---------|
| `consumeInbound()` | `AgentLoop.run()` | 独占轮询，拿到消息后交给状态机处理 |
| `consumeOutbound()` | `ChannelManager._dispatchLoop()` | 独占轮询，按 `msg.channel` 字段路由到对应 Channel |

### 17.3.2 "resolve-or-queue"——97 行里最精妙的三行

`publishInbound` 只有 5 行，但它的设计体现了 CatBuddy 对"简洁"的理解：

```ts
publishInbound(msg: InboundMessage): void {
  if (this._inboundResolve) {
    this._inboundResolve(msg);   // ← 关键：直接交付，不走队列
    this._inboundResolve = null;
  } else {
    this._inbound.push(msg);     // ← 没人在等，先存着
  }
}
```

**如果消费者正在 `await consumeInbound()` 等待，生产者直接把消息交给那个等待的 Promise——消息不出现在队列里。** 只有消费者不在等待时（比如正在处理上一条消息），消息才进入 `_inbound` 数组排队。

这意味着：
- **热路径零内存开销。** AgentLoop 空闲等待时，入站消息直接 resolve，不走数组 push/shift。没有 GC 压力。
- **队列只存"未消费的积压"。** `_inbound` 数组的长度反映的是真实积压量，而不是"历史上总共发过多少消息"。这对于监控和调试非常有意义。
- **单消费者天然线程安全。** 不存在两个消费者抢同一个消息的问题。`_inboundResolve` 在被 resolve 后立即置 `null`，新的 `publish` 调用自动走队列路径。

同样的模式对称地应用在 outbound 方向。`ChannelManager._dispatchLoop()` 阻塞在 `consumeOutbound(1000)` 上，AgentLoop 的流式回调 `publishOutbound` 时直接 resolve。

### 17.3.3 入站侧：四个生产者，一个入口

谁在往 `publishInbound` 写消息？不只一个来源：

**1. IPC 处理器——Desktop 用户输入**

用户在前端输入框里打字，Electron IPC 把消息传到主进程：

```ts
// apps/desktop/src/main/ipcHandlers/index.ts
ipcMain.handle('agent:send', async (_event, { chatId, content, ... }) => {
  bus.publishInbound({
    channel: 'desktop',
    senderId: 'user',
    chatId: bareChatId(sessionKey),
    content,
    media: media ?? [],
    timestamp: Date.now(),
  });
});
```

这是最常见的一条路径——用户在 Desktop 应用里发消息。

**2. Heartbeat 定时器——Agent 的"自主意识"**

CatBuddy 有一个每 30 分钟触发一次的心跳机制。它不依赖用户输入，而是通过 `CronScheduler` 定时检查工作区里的 `HEARTBEAT.md` 文件，如果里面有未完成的任务，就自动发一条消息唤醒 Agent：

```ts
// apps/desktop/src/main/heartbeat/index.ts
export function runHeartbeatOnce(runtime: DesktopRuntimeRefs) {
  const msg: InboundMessage = {
    channel: "desktop",
    senderId: "heartbeat",          // ← senderId 标识来源
    chatId: "main",
    content: buildHeartbeatPrompt(),
    metadata: { heartbeat: true },  // ← metadata 标记让前端特殊处理
  };
  bus.publishInbound(msg);
}
```

这条消息对 AgentLoop 来说和用户发的消息没区别——它只是 `consumeInbound()` 拿到的下一条 `InboundMessage`。AgentLoop 的 `_dispatch` 方法会检查 `isHeartbeatMessage(msg)`，如果是心跳消息，就抑制出站流式输出（不在 UI 上刷屏），但仍然执行任务。

**3. Sub-Agent 管理器——子 Agent 的结果注入**

子 Agent 在后台跑完后，结果不是通过 AgentRunner 的正常响应路径回来的——因为主 Agent 可能正在干别的事。子 Agent 的结果直接走 `bus.publishInbound()` 注入回主 Agent 的对话流：

```ts
// apps/desktop/src/main/agent/subagent.ts
private async _announceResult(...): Promise<void> {
  const msg: InboundMessage = {
    channel: 'system',              // ← system 通道
    senderId: 'subagent',           // ← 标识来源为 subagent
    chatId: `${origin.channel}:${origin.chatId}`,
    content: renderedResult,
    metadata: {
      injected_event: 'subagent_result',  // ← 前端据此做差异化展示
      subagent_task_id: taskId,
    },
  };
  this.bus.publishInbound(msg);
}
```

注意这里用的是 `channel: 'system'` 和 `senderId: 'subagent'`。前端可以根据 `injected_event` 字段渲染特殊的"子 Agent 完成"卡片，而不是当成普通用户消息。但 AgentLoop 不关心这些——对它来说，这只是下一条入站消息，继续处理就好。

**4. Gateway Desktop Client——远程 Web 用户输入**

Web 用户在浏览器里打字，消息经过 Gateway Server 转发到 Desktop 主进程的 `GatewayDesktopClient`，最终也是走 `bus.publishInbound()`：

```ts
// GatewayChannel 内部
this.gateway.onUserMessage((data) => {
  bus.publishInbound({
    channel: 'gateway',
    senderId: 'gateway-web',
    chatId: data.chatId,
    content: data.content,
    ...
  });
});
```

**四种生产者，一条总线，一个消费者。** AgentLoop 的 `run()` 方法就是一个死循环：

```ts
// apps/desktop/src/main/agent/loop.ts
async run(): Promise<void> {
  this._running = true;
  while (this._running) {
    const msg = await this.bus.consumeInbound();  // ← 阻塞等待
    if (!msg) continue;                           // 超时，继续等

    // 优先命令（/stop 等）立即响应，不走 Agent 推理
    if (this.commands.isPriority(msg.content)) {
      const result = await this.commands.dispatchPriority(cmdCtx);
      if (result) await this.bus.publishOutbound(result);
      continue;
    }

    // 普通消息 → Agent 推理
    this._dispatch(msg).catch(err => console.error(err));
  }
}
```

AgentLoop 不 import IPC、不 import Cron、不 import SubagentManager。它只认识 `MessageBus`。这就是解耦的力量。

### 17.3.4 出站侧：九个回调 → 一种消息

入站侧的生产者多样化，出站侧的生产者却只有**一个**——AgentLoop 的 `_dispatch` 方法。但它内部有 9 种不同的流式回调：

```ts
// apps/desktop/src/main/agent/loop.ts  _dispatch() 内部
onStreamDelta: (delta) => {
  this.bus!.publishOutbound({
    channel: msg.channel, chatId: msg.chatId,
    content: delta,
    metadata: { _stream_delta: true, _stream_id: streamId() },
  });
},
onReasoningDelta: (content) => {
  this.bus!.publishOutbound({
    channel: msg.channel, chatId: msg.chatId,
    content, metadata: { _reasoning_delta: true },
  });
},
onToolProgress: (ev) => {
  this.bus!.publishOutbound({
    channel: msg.channel, chatId: msg.chatId,
    metadata: { _tool_progress: true, tool_event: ev },
  });
},
onFileEdit:      (edit)  => { ... metadata: { _file_edit: true, ... } },
onDiagramEvent:  (event) => { ... metadata: { _diagram_event: true, ... } },
onTurnComplete:  (data)  => { ... metadata: { _turn_complete: true, ... } },
onSystemMessage: (text)  => { ... metadata: { _progress: true }, content: text },
onRetryWait:     (msg)   => { ... metadata: { _progress: true }, content: msg },
onAssistantMessage: (text) => { ... metadata: { _assistant_complete: true }, content: text },
```

注意这个设计：**9 种语义不同的事件，共用同一种 `OutboundMessage` 结构。** 区分它们的不是事件名（没有 `event: 'delta'` 这样的字段），而是 `metadata` 里的布尔标记——`_stream_delta`、`_tool_progress`、`_file_edit` 等等。

这又是 CatBuddy 的一个设计选择：**不进 `OutboundMessage` 加 `type` 字段**，而是用 `metadata` 做标记。好处是：
- `OutboundMessage` 的结构保持极简（channel + chatId + content + metadata + buttons），不会因为事件类型增加而膨胀。
- 新增一种流式事件只需加一个 `_xxx: true` 标记，不需要改接口定义。
- `metadata` 本身就是透传的，不需要额外维护一个 event type 枚举。

### 17.3.5 ChannelManager：出站消费者与路由

出站消息由谁消费？`ChannelManager._dispatchLoop()`：

```ts
// apps/desktop/src/main/channels/manager.ts
private async _dispatchLoop(): Promise<void> {
  while (this._running) {
    const msg = await this.bus.consumeOutbound(1000);  // 阻塞等待
    if (!msg) continue;

    const targets = this.targetsFor(msg);  // 按 msg.channel 路由
    for (const channel of targets) {
      await this._deliver(channel, msg);   // 调用 channel.send*() 系列方法
    }
  }
}
```

`_deliver` 方法根据 `metadata` 里的标记分发到 Channel 的不同方法：

```ts
private async _deliver(channel: BaseChannel, msg: OutboundMessage): Promise<void> {
  const meta = msg.metadata ?? {};
  if (meta._stream_delta)        await channel.sendDelta?.(msg.chatId, msg.content);
  if (meta._reasoning_delta)     await channel.sendReasoningDelta?.(msg.chatId, msg.content);
  if (meta._tool_progress)       await channel.sendToolProgress?.(msg.chatId, meta.tool_event);
  if (meta._file_edit)           await channel.sendFileEdit?.(msg.chatId, meta.file_edit);
  if (meta._turn_complete)       await channel.sendTurnComplete?.(msg.chatId, meta.turn_complete);
  // ...
}
```

还有一个关键的路由逻辑在 `targetsFor` 里——**Desktop Channel 的消息要 fan-out 到 Gateway Channel**：

```ts
private targetsFor(msg: OutboundMessage): BaseChannel[] {
  const primary = this.channels.get(msg.channel);
  const out: BaseChannel[] = [];
  if (primary) out.push(primary);
  if (msg.channel === "desktop") {
    const gateway = this.channels.get("gateway");
    if (gateway) out.push(gateway);  // Desktop 出站也同步到 Gateway
  }
  return out;
}
```

这意味着用户在 Desktop 上看到的内容，Web 端也能看到——因为桌面端的出站消息被"广播"到了 Gateway Channel。这是 CatBuddy 多端同步的基础。

### 17.3.6 Bus 就是系统的"心跳"

回到 `AgentLoop.run()` 的主体结构：

```ts
while (this._running) {
  const msg = await this.bus.consumeInbound();
  if (!msg) continue;  // 1秒超时，没人说话就继续等
  // ... 处理消息
}
```

这个 `while` 循环是 CatBuddy 进程的**主循环**。AgentLoop 的生命就是：
1. 阻塞在 `consumeInbound()` 上，等 1 秒
2. 超时返回 `null`，`continue` 回到第 1 步
3. 如果有消息，处理它
4. 处理完后回到第 1 步

Bus 的 `consumeInbound` 不只是一个"取消息"的工具——它是 AgentLoop 的**时钟**。1 秒的超时不是性能问题（`await` 不占 CPU），而是一个优雅的"无事可做时的事件循环让渡"——让 Node.js 在这 1 秒里去处理 IPC 回调、文件 I/O、定时器。

### 17.3.7 完整消息往返

把 Bus 放在三段式架构的中心，一次完整的消息往返是这样的：

```text
用户在 Desktop 输入 "帮我重构这个函数"

  IPC Handler: bus.publishInbound({ channel:'desktop', senderId:'user', content:'帮我重构...' })
      │
      ├─ AgentLoop 正在 consumeInbound() 等待
      │  → _inboundResolve 不为空 → 直接 resolve，消息不入队
      ▼
  AgentLoop.run(): msg = await consumeInbound()  // 拿到消息
      │
      ▼
  _dispatch(msg):
    ├─ AgentRunner.run() → LLM 推理
    │
    ├─ onStreamDelta("好")  → bus.publishOutbound({ metadata: { _stream_delta: true } })
    ├─ onStreamDelta("的")  → bus.publishOutbound({ metadata: { _stream_delta: true } })
    ├─ onToolProgress(...)  → bus.publishOutbound({ metadata: { _tool_progress: true } })
    ├─ onFileEdit(...)      → bus.publishOutbound({ metadata: { _file_edit: true } })
    └─ onTurnComplete(...)  → bus.publishOutbound({ metadata: { _turn_complete: true } })
      │
      ├─ ChannelManager._dispatchLoop 正在 consumeOutbound() 等待
      │  → 每条 publishOutbound 直接 resolve
      ▼
  ChannelManager._deliver():
    ├─ _stream_delta  → WebUIChannel.sendDelta()    → IPC → UI 渲染
    ├─ _tool_progress → WebUIChannel.sendToolProgress()
    └─ _turn_complete → WebUIChannel.sendTurnComplete()
                       → GatewayChannel.sendTurnComplete()  (fan-out)
```

整个过程，**AgentLoop 的代码里没有任何 `ipcMain`、`BrowserWindow` 或 `WebSocket` 的引用。它只对 `MessageBus` 说话。**

把 Bus 放在 CatBuddy 的全景图里看，它就是那个被所有箭头穿过的中心圆：

```text
                  ┌──────────────┐
                  │  IPC Handler │──┐
                  └──────────────┘  │
                  ┌──────────────┐  │  publishInbound

                          │
                          ▼
                   ┌─────────────┐
```

97 行代码，连接了整个系统的所有模块。这就是 MessageBus——CatBuddy 的脊椎神经。

---

## 17.4 总结

> **这篇讲了什么？**
>
> 1. CatBuddy 的传输层是"二层抽象一个总线"的三段式架构：`AgentTransport` 接口对 UI 端提供可插拔的事件订阅（三种实现：IPC / Gateway WS / 直连 WS），`BaseChannel` 接口对 Agent 端提供类型化的消息发送（WebUIChannel / GatewayChannel），`MessageBus` 作为生产者-消费者队列把两端彻底解耦。
> 2. `createAgentTransport()` 工厂函数通过 `!!window.catbuddy` 自动检测运行环境，一行代码切换传输模式。上层 `catbuddyClient` 完全不感知底层是 IPC 还是 WebSocket。
> 3. 两端的接口设计有不对称性——UI 端收敛为单一 `onEvent` 回调（方便 `switch` 分发），Agent 端细分为 9 种 `send*()` 方法（类型化参数约束）——这是不同消费者的真实需求决定的，不是设计不一致。
